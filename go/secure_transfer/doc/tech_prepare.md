# 技术准备

## 标准非对称加解密流程

非对称加解密是使用公钥加密、私钥解密的过程。假设是甲向乙传递消息，则是甲使用乙的公钥加密、乙使用自己的私钥解密。

标准非对称加密过程：（以下内容中，`P`表示公钥、`p`表示私钥）

1. 甲随机生成密钥对`(P1,p1)`
2. 使用私钥`p1`与乙的公钥`P2`进行协商，得到共享密钥`s`

- 数学上，`p1+P2`和`p2+P1`派生出的共享密钥`s`相同

3. 使用共享密钥`s`派生出最终加密秘钥`k`

- 派生过程中会用到盐`salt`，这是一串随机生成的字符序列
- 派生通常就是hash，相同环境下多次派生的结果相同

4. 使用最终加密秘钥`k`加密原文`plaintext`得到密文`ciphertext`

- 加密过程中用到`nonce`，这是一串随机生成的字符序列
- 这里使用对称加密，所以`k`同时也是最终解密秘钥

5. 将甲的公钥`P1`、`salt`、`nonce`拼在密文前面（还可以拼其他参数），得到最终加密结果`encrypted file`

- 流式加密中，因为每一帧都要用不同的nonce，所以nonce不是写在文件头，而是写在每一帧的开头

标准非对称解密过程：

1. 乙拿到最终加密结果`encrypted file`，读取并反序列化出：`P1`、`salt`、`nonce`、`ciphertext`
2. 使用私钥`p2`与`P1`进行协商，得到共享密钥`s`
3. 使用共享密钥`s`派生出最终解密秘钥`k`
4. 使用最终解密秘钥`k`解密密文`ciphertext`得到明文`plaintext`

## 椭圆曲线密码学

Elliptic Curve Cryptography 椭圆曲线密码学 (ECC)
Elliptic Curve Digital Signature Algorithm 椭圆曲线数字签名算法 (ECDSA)

背景知识：（以ethereum为例，大写表示可以公开）

- 椭圆曲线上的一个点，我们为其定义了加法和乘法运算
- 假设公钥为K、私钥为k、曲线基点为G，有K=kG
- 私钥：256 bits随机数；公钥：512 bits；地址：160 bits
- 私钥 - (椭圆曲线乘法)-> 公钥 - (Keccak-256 hash & 取后20字节)-> 地址

不同平台之间各有不同，但总体上多是：根据私钥计算公钥、根据公钥计算地址

## 加、解密

使用随机数r将明文消息M生成密文C，该密文是一个点对： C = {rG, M+rK}

解密则是使用C、k还原M的过程： M = M + rkG - rkG = (M + rK) - k (rG)
即用C的第二个点减去k乘以第一个点，得到的结果就是明文M

- 前文提到：公钥K=私钥k*基点G

## 签名验签 (?)

签名：

- 对明文做hash，得到H（256 bits）
- K=k*G，取r=K.x
- s = k⁻¹ * (H + r * k) mod n
    - k⁻¹ 是 k 在模 n 下的模逆元
    - n 是曲线的阶
- v: 标识K.y是奇数还是偶数
- 签名结果： (r, s, v)

验签：可以拿到消息hash H和签名结果 (r, s, v)

- 根据H和签名可以恢复出公钥，根据公钥计算出地址A，即可以确认这个签名是A签的

## DH交换算法 (Diffie-Hellman)

DH算法是一种在不安全的通信信道上安全地交换密钥的协议。算法只协商密钥，不负责加密

原理是在数学问题中，正着计算过去相对容易，而反着推则非常困难。

过程：（大写字母表示可以公开）

- 甲和乙约定两个数P和G
- 甲使用随机数a计算 A = G^a (mod P)
- 乙使用随机数b计算 B = G^b (mod P)
- 甲、乙交换A、B
- 甲计算 S = B^a (mod P)
- 乙计算 S = A^b (mod P)
- 在数学上，两人计算出的S相同

ECDH算法则是结合了椭圆曲线的密钥协商算法，X25519是比较常用的一种

## 密钥派生函数 KDF Key Derive Function

绝大多数现代协议都不会直接使用原始密钥，而是先经过 KDF。

为什么需要KDF：

- 协商出的密钥可能并不均匀
- 一个共享密钥可能需要派生出多个密钥
- 密钥隔离
- 绑定更多上下文

## 混合加密

非对称加密的数学算法在实际应用中有着诸多限制：

- 对原文长度有要求，加密的数据量不能超过密钥阶数，即一个2048位的密钥单次只能加密256字节的数据
- 速度慢，考虑到cpu的针对性指令集，对称加密比非对称加密快100～1000倍

所以在实际应用中，即使宣称使用非对称加密技术，其底层实际用于加密的算法，大多也是对称加密，例如以太坊go sdk (ecies)

## 加密nonce

aes-gcm算法一定不要使用相同的nonce多次加密，有很高的安全风险。所以我们在设计的过程中：

- 一次性加密每次加密文件重新生成`fileHeader`（随机生成新的nonce）
- 流式加密每一帧使用不同的nonce（通过帧索引）

## 流式加密

> 本节只讨论加密过程，解密过程类似

一次性加密有一个无法回避的缺点：内存占用，它需要把文件全部内容加载到内存中，遇到内存不足的情况更是会直接失败，
所以考虑对大文件使用流式加密。

流式加密即是同时持有原始文件和加密文件的句柄，将整个加密过程拆分成许多帧，每一帧包含读取、加密、写入三个步骤。

> 假设每个步骤分别用时`a`/`b`/`c`

基础的流式加密需要等待一帧完成才能执行下一帧，此时每一帧用时`sum(a,b,c)`

而如果采用流水线模型，即读取一帧之后立刻读取下一帧，此时每一帧用时`max(a,b,c)`（流水线运行起来之后）

这时候再想要提高性能，可以并发处理耗时最长的步骤，例如我们在代码中会开启多个加密goroutine
