# 设计

## 方案

使用椭圆曲线协商算法得到共享密钥，共享密钥派生得到最终加密密钥，使用对称加密算法加密

- 曲线与密钥协商算法：Curve25519 X25519
- 最终加密密钥派生算法：sha256
- 对称加密算法：aes-gcm
- 加密方式：
    - 文件大小 <10m：一次性读取到内存加密
    - 文件大小 >10m：流式加密

程序中同时保留一次性加密和流式加密两种加密方式，主要是考虑到：

1. 如果小文件也使用流式加密将导致：运行速度变慢、分配内存更多以及可能会产生中间文件（非首帧验证失败）
2. 流式加密可以进一步优化，导致流式加密的代码一眼看上去找不到重点，所以保留一次性加密的代码用作功能流程简述。流式加密优化方向：
    - 读文件、加密、写文件并发进行
    - 加密过程多goroutine并发执行
    - channel通信过程中的异常处理（阻塞、退出等）
    - 每一帧的加解密都会分配一些很快就会作废的大对象，使用缓冲池复用这些对象

## 加密文件编码规则

程序采用`技术准备-标准非对称加解密流程`小节中的流程，本节定义并详细介绍`哪些内容拼在密文前面`

```txt
header len + 
'ST' + enc method + 
salt len + base nonce len + pubK len + aad len +
salt + base nonce + pubK + aad + 
ciphertext
```

- `header len`：整个文件头（一直到正文之前）的长度
    - 本工具中长度固定为94，即加密文件将固定以`^ST`开头
    - 94 = (2+1) + 4 + (16+7+32+32)
- `ST`：开头标记，项目名secure transfer的简写
- `enc method`：一次性读取到内存中加密/流式加密
- `salt`：用于密钥派生的salt
    - 本工具中长度固定为16
- `base nonce`：aes-gcm base nonce
    - 本工具中长度固定为7
    - 一次性加密nonce：base nonce后面补0凑够位数
    - 流式加密nonce：7+1+4，base nonce + 末帧标识 + 帧索引
- `pubK`：用于解密-协商密钥的公钥
    - 本工具中长度固定为32
- `aad`：文件头除了aad以外的环节的hash，长度为32
- `ciphertext`：密文
    - 流式加密密文（一帧）：
        - 末帧标识：1 Byte
        - 帧索引：4 Byte
        - 有效内容长度：4 Byte
        - 有效内容：x Byte

## 实现

一次性加密：

1. 从文件加载公钥
2. 尝试匹配明文文件
    - 根据文件名匹配：`message.xxx`，第一个符合该规则的文件即为明文文件
    - 如果没有匹配到相关文件则报错并退出
3. 根据文件大小选择加密方式：一次性加密或流式加密
4. 加密明文并写入新文件

一次性解密：

1. 从文件加载私钥
2. 尝试匹配密文文件
3. 读文件头，得到加密方式，选择对应的解密方式
4. 解密密文并写入新文件

根据前期技术准备，我们对流式加密进行优化：读文件、加密、写文件并发执行；加密过程开多个goroutine并发执行
